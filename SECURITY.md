# AfterImpact — Security

This document owns the security posture: the threat model, all security and privacy requirements, the controls that enforce them, and trust-boundary enforcement. `REQUIREMENTS.md` owns WHAT the system does; `ARCHITECTURE.md` owns components, boundaries, and data flow, and defines the `UNKNOWN` / `TO BE DECIDED` / `ASSUMPTION` markers used here; `DESIGN.md` owns client-facing interaction conventions.

Security requirements carry `NFR-1.*` (security) and `NFR-2.*` (privacy) IDs, stated inline on the rule that owns each one. Controls carry `SEC-*` IDs; dependency rules carry `DEP-*`. No implementation exists yet, so every rule here is prospective and no conformance is claimed.

## Security Profile

- **Sensitive data:** Every record the system holds is treated as sensitive personal data because it includes health information (D-5) — the entities in `REQUIREMENTS.md` **Data Entities**, plus passkey credential material and the security event log. Contact records and journal narrative additionally hold personal data about **third parties** (the other driver, witnesses, employer, adjusters) who are not the account owner; under the household/personal-use frame the account owner acts as data controller for these records, the system owes the third parties no direct duties, the privacy policy states this, AfterImpact never contacts them, and breach handling covers the account owner only (resolves SQ-15; T-50).
- **Actors and authorization model:** One actor, the accident victim, as sole account owner; a single role; owner-only access to every record (D-2, FR-1.9).
- **Authentication model:** Passkeys are the only factor that grants normal account access (FR-1.2, D-9). Amazon Cognito also enables email OTP because it cannot configure `WEB_AUTHN` as its sole first factor; the initial ceremony verifies the submitted address, and later recovery uses that verified address. The API converts successful OTP ceremonies only into restricted first-passkey bootstrap or lost-passkey recovery sessions. Password and SMS authenticators are disabled, and no user-chosen shared-secret credential exists (SEC-AUTHN-9).
- **Trust boundaries:** The four boundaries in `ARCHITECTURE.md` **Trust boundaries**, referred to below as boundaries 1, 2, 3, and 4. Boundary 4 (system ↔ managed identity provider) is governed by SEC-SESSION-3 and the exact `WEB_AUTHN` + `EMAIL_OTP` factor policy recorded in `ARCHITECTURE.md`'s Technology Decisions.
- **External attack surface:** Boundary 1 (clients), boundary 3 (outbound email), and boundary 4 (the managed identity service); no inbound third-party integration exists in v1 — outbound email and the identity service are the external service dependencies (D-7, as amended).
- **Regulatory obligations:** No health-specific regime (HIPAA or similar) applies — there is no covered entity or business-associate relationship (resolves SQ-1). All records are nonetheless handled as sensitive health data (D-5), and consumer-privacy duties follow the global GDPR-grade bar recorded as D-10 in `REQUIREMENTS.md` (resolves OQ-1). One pre-launch legal review is commissioned as a SEC-DEPLOY-4 release gate, covering health-content and unlicensed-practice exposure, the sufficiency of the FR-4.9 and FR-5.8 notices, and accessibility obligations in the launch markets; its outcomes are recorded in the documents that own them. Until it reports, the per-requirement **Jurisdiction / Regulatory Scope** and **Regulatory** mappings `REQUIREMENT_TEMPLATE.md` calls for stay `TO BE DECIDED` — a marker deliberately retained to record an unassessed state, never to be replaced by a guessed mapping.
- **Assurance target:** OWASP ASVS 5.0.0 Level 2, pinned (resolves SQ-8): a structured self-assessment against every Level 2 requirement runs pre-launch, tracked as a repository checklist; independent assessment is revisited post-launch (SEC-DEPLOY-4).
- **Threat model:** AUTHORED (2026-08-13). The **Threat Model** section below enumerates threats `T-1`–`T-51` against the documented system, naming the product-specific adversaries — the hostile opposing party in the insurance/legal dispute, the household adversary with device access, the attacker controlling the user's email account, the malicious or compromised infrastructure operator, and automated/supply-chain abuse — alongside the everyday actors. Each threat cites its existing controls and — following the 2026-08-13 decision pass that resolved every cited open question — the resolution that closed it. The rules below are the controls the table references (T-45).

## Security and Privacy Rules

Grouped by capability; one verifiable behavior per rule. A rule that carries an `NFR-*` ID **is** that requirement — it is stated here and nowhere else. Per-rule status is in **Traceability**; every value formerly marked `TO BE DECIDED` inside a rule was resolved on 2026-08-13 and is stated inline.

### Trust boundaries and server-side enforcement

- **SEC-TRUST-1** The REST API application MUST enforce every business rule, validation, and authorization decision server-side; client-side checks are responsiveness aids only and MUST NOT be relied on at boundary 1.
  - **Applies to:** All operations crossing trust boundary 1
  - **Verification:** API-level tests exercising every rule with the client bypassed (direct HTTP)
  - **References:** `REF-ASVS-5`, `REF-PC-2024`, `REF-INPUT`
- **SEC-TRUST-2** The RDBMS, the file store, backup artifacts, and any additional store that holds personal data (for example a separate search index, if the ratified database-search decision in `ARCHITECTURE.md` is ever revisited) MUST be reachable only by the API application and background worker; no client, public network path, or other component may cross boundary 2. The rule binds any store holding personal data, not only the two originally named (T-19, T-31).
  - **Applies to:** API ↔ stores boundary; backup storage; any derived personal-data store
  - **Verification:** Infrastructure review plus network reachability tests from outside the private boundary
  - **References:** `REF-ASVS-5`, `REF-IAC`, `PRM-TF`
- **SEC-TRUST-3** (**NFR-1.5**) User-uploaded content MUST be treated as hostile whenever it crosses back toward clients, and MUST be delivered such that it cannot execute as active content (scripts/HTML) in the application's origin.
  - **Applies to:** Document view/download paths through the API
  - **Verification:** Tests that uploaded HTML/SVG/script content never executes in the app origin
  - **References:** `REF-XSS`, `PRM-UPLOAD`
- **SEC-TRUST-4** Every hop inside trust boundary 2 MUST be transport-encrypted, not merely private-network-isolated: database connections MUST use TLS with full certificate verification — chain and hostname both checked against a pinned trust store, with no fallback to an unverified or cleartext connection — and all file-store access MUST use HTTPS, with the store configured to refuse non-TLS requests. The rule binds the API application, the background worker, and backup and restore traffic alike. A private network is not a confidentiality boundary against the malicious or compromised infrastructure operator (T-13), who can observe traffic between services that SEC-DATA-1's at-rest encryption does not reach; SEC-TRUST-2 keeps other parties off the boundary, and this rule protects what crosses it.
  - **Applies to:** API ↔ stores boundary; backup and restore traffic
  - **Verification:** Connection-configuration review; negative tests asserting that a server presenting an untrusted or hostname-mismatched certificate is refused and that a cleartext connection attempt fails
  - **References:** `REF-ASVS-5`, `PRM-TF`, `PRM-QUARKUS`

### Authentication

- **SEC-AUTHN-1** Normal account sessions MUST use passkeys (WebAuthn) (FR-1.2). Registration and assertion ceremonies are performed by the managed identity provider (`ARCHITECTURE.md`), which MUST validate each ceremony fully server-side — challenge freshness and single use, origin and RP ID binding, signature; the API application MUST NOT accept client-asserted authentication results and accepts identity only through the server-side Cognito exchange (SEC-SESSION-3). `EMAIL_OTP` is the only additional first factor enabled at Cognito and MUST result only in the restricted bootstrap/recovery session SEC-AUTHN-6 defines, never a normal account session. These properties are verified against the identity-provider integration configuration.
  - **Applies to:** Identity & session handling; sign-in and passkey registration ceremonies
  - **Verification:** Negative tests with replayed challenges, wrong origin/RP ID, and tampered assertions
  - **References:** `REF-WEBAUTHN`, `REF-FIDO`, `REF-63B-4`, `PRM-PASSWORDLESS`
- **SEC-AUTHN-2** WebAuthn user handles MUST be opaque random values that encode no email address or other identifying data, and stored credential material MUST be limited to what verification requires (credential ID, public key, per-owner binding). Credential material is held by the managed identity provider (`ARCHITECTURE.md`); these properties are verified against its integration configuration rather than first-party storage.
  - **Applies to:** Identity & session handling credential storage
  - **Verification:** Cognito integration review; test that user handles are random and non-identifying and that first-party storage contains no extra credential material
  - **References:** `REF-WEBAUTHN`, `PRM-PASSWORDLESS`
- **SEC-AUTHN-3** The system MUST require email verification before an account becomes usable for sign-in, and re-verification when the email address changes (FR-1.1, FR-1.7).
  - **Applies to:** Registration and email-change flows
  - **Verification:** Functional tests: unverified accounts cannot sign in; email change requires re-verification
  - **References:** `REF-AUTH`, `PRM-RECOVERY`
- **SEC-AUTHN-4** The system MUST throttle failed passkey and email-OTP attempts per account at the FR-1.4 thresholds and MUST log each lockout to the security event log. Because a purely account-scoped block is a renewable denial-of-service lever against the owner (T-1), the system MUST also apply source-based and anti-automation throttling ahead of the account block (values in SEC-HTTP-6). The account block MUST prevent further OTP guesses but MUST NOT prevent a successful valid passkey ceremony by the owner (a valid assertion is proof of possession, not a guess).
  - **Applies to:** Identity & session handling
  - **Verification:** Automated tests driving repeated failures, asserting lockout, source-throttling, and log entry; test that a valid ceremony succeeds during an account block
  - **References:** `REF-AUTH`, `PRM-RATE`
- **SEC-AUTHN-5** All authentication and account-mail flows MUST respond identically whether or not an account exists; no response content, observable behavior, or email side effect may disclose account existence (FR-1.3).
  - **Applies to:** Sign-in, registration, recovery, email change
  - **Verification:** Response- and timing-equivalence tests for existing vs. non-existing accounts, including that FR-1.4 throttling presents identically for nonexistent accounts (T-9)
  - **References:** `REF-AUTH`, `REF-WEBAUTHN`, `REF-ERROR`
- **SEC-AUTHN-6** The first-passkey bootstrap and lost-passkey recovery flows required by FR-1.2 and FR-1.6 use a one-time email code (resolves SQ-2): initial bootstrap sends it to and thereby verifies the submitted address; recovery sends it to the already-verified account address. The code MUST be single-use, MUST expire after 10 minutes, and MUST be subject to SEC-AUTHN-4 and SEC-HTTP-6. A successful code ceremony MUST create a separately scoped server-side session that expires after 10 minutes and permits exactly one operation: registration of a new passkey. It MUST NOT authorize reading, changing, exporting, or deleting any account or case data. Successful passkey registration MUST invalidate every other active session, consume the restricted session immediately, and send a security notice to the verified email address (SEC-AUTHN-11). Recovery responses MUST be enumeration-safe and timing-equivalent (SEC-AUTHN-5, T-9), and recovery mail MUST honor SEC-EXT-4. This design accepts control of the verified mailbox as the recovery trust anchor; a mailbox-controlling attacker can register a replacement passkey, and that residual is recorded in T-2.
  - **Applies to:** Identity & session handling
  - **Verification:** Tests of 10-minute code and restricted-session expiry, single use, operation scoping, session invalidation and notice on passkey registration; enumeration- and timing-equivalence tests on the recovery flow
  - **References:** `REF-63B-4`, `REF-AUTH`, `REF-FIDO`, `PRM-RECOVERY`
- **SEC-AUTHN-7** Account deletion MUST require a fresh passkey authentication ceremony by the account owner, completed within the same session and immediately before deletion (FR-9.3). Freshness is server-side state, never a client claim (resolves SQ-17): a successful ceremony MUST stamp the server-side session with its completion time, and that stamp MUST authorize any guarded operation for 5 minutes, so one ceremony may cover several — a user working through account-security changes is not re-prompted per click. The API MUST evaluate the stamp on every guarded request and MUST refuse a request whose stamp is absent or older than 5 minutes with a distinct machine-readable refusal code, separate from ordinary authentication and authorization failures, so a client prompts for the ceremony instead of inferring the reason from a generic error; the refusal MUST perform no part of the guarded operation.
  - **Applies to:** Account deletion flow; every operation guarded by SEC-AUTHN-10
  - **Verification:** Test that deletion is refused without a fresh re-authentication ceremony; clock-advanced tests asserting the stamp lapses after 5 minutes, that one ceremony covers several guarded operations inside the window, and that a stale or absent stamp returns the distinct refusal code with no state change
  - **References:** `REF-AUTH`, `REF-63B-4`
- **SEC-AUTHN-8** Credential registration and revocation (FR-1.8) MUST be available to the signed-in user, MUST refuse a revocation that would leave the account with no usable authentication path, and MUST send a notification to the verified email address. While only one passkey is registered, the system MUST prompt the user to register a second (T-2).
  - **Applies to:** Identity & session handling; credential lifecycle
  - **Verification:** Functional tests of the credential list, revocation guard, and notification; test that the second-passkey prompt appears while a single credential exists
  - **References:** `PRM-PASSWORDLESS`, `REF-FIDO`
- **SEC-AUTHN-9** (**NFR-1.3**) The system MUST NOT store or accept any user-chosen shared secret — password, PIN, or knowledge-based answer — as an authentication factor. The system-generated, single-use `EMAIL_OTP` allowed by D-9 is not user-chosen and is constrained to SEC-AUTHN-6's bootstrap/recovery session. If a persistent shared-secret credential is ever introduced, it requires a security review and MUST be stored using a memory-hard adaptive hashing scheme consistent with current OWASP Password Storage guidance, never recoverable by the system.
  - **Applies to:** Identity & session handling
  - **Verification:** Schema review asserting no shared-secret credential field exists
  - **References:** `REF-63B-4`, `REF-AUTH`, `PRM-PASSWORDLESS`
- **SEC-AUTHN-10** High-impact account-security and full-data-egress operations MUST require a fresh passkey authentication ceremony by the owner, completed within the same session immediately before the operation — extending the SEC-AUTHN-7 pattern (which already guards account deletion) to: email-address change (FR-1.7), passkey registration and revocation (FR-1.8), full-account export (FR-9.2), and case deletion (FR-2.6) (case-deletion step-up resolves SQ-16 in part; T-12). The only exception is SEC-AUTHN-6: its restricted email-OTP session may register exactly one first or replacement passkey and perform nothing else. Each operation named here is a guarded operation under SEC-AUTHN-7's ceremony, and takes that rule's 5-minute session stamp and distinct refusal code unchanged — the freshness contract is stated there and nowhere else. This closes the asymmetry whereby a transient normal-session compromise could silently take over the account or exfiltrate the entire record set without re-proving possession of a passkey (T-3, T-11).
  - **Applies to:** Identity & session handling; REST API application; Background processing (export)
  - **Verification:** Tests that each listed operation is refused, with the SEC-AUTHN-7 refusal code, without a fresh re-authentication ceremony in the same session
  - **References:** `REF-AUTH`, `REF-63B-4`, `PRM-PASSWORDLESS`
- **SEC-AUTHN-11** The system MUST send an out-of-band notification to the account's verified email address when a security-significant event occurs, so an attacker operating a stolen session cannot act entirely silently through the in-app feed they control (T-3, T-4, T-11, T-27, T-46). At minimum: email-address change (to **both** the prior and the new address), full-account export creation (FR-9.2), account-deletion initiation (FR-9.3), and case deletion (FR-2.6); passkey registration and revocation are already notified under SEC-AUTHN-8. A sign-in from a not-previously-recognized context MUST also notify: a sign-in is unrecognized when the device/browser has not previously been seen for the account, with IP/geolocation as secondary signals (resolves SQ-16; T-4, T-27). Recognition is carried by the `Device` entity `REQUIREMENTS.md` **Data Entities** models (resolves SQ-19); its identifier MUST be opaque and randomly generated and MUST NOT be derived from a device fingerprint or any other identifying attribute, the web client anchoring it in a dedicated cookie and the mobile client generating it and holding it in platform secure storage (SEC-SESSION-6). The recognition set MUST be capped at 10 devices per account, evicting the least-recently-seen device when a new one arrives, so the notice keeps its meaning: 10 covers a phone, a tablet, a laptop, a work machine, and several browser profiles, making eviction rare enough that a re-notification is worth the owner's attention. The records are disclosed in the privacy policy (SEC-DATA-7). These are security messages: they MUST NOT be suppressible by the FR-5.6 email-reminder toggle, are exempt from SEC-HTTP-6's per-recipient email cap, and MUST honor SEC-DATA-6 (no health or document content in the mail).
  - **Applies to:** Identity & session handling; Background processing; Outbound email boundary (external); Web client; Mobile client
  - **Verification:** Tests asserting a notice per listed event, delivery to the prior address on email change, and non-suppression by the reminder toggle; tests that an unseen device notifies, that a device beyond the cap evicts the least-recently-seen entry, and that the identifier is opaque and non-identifying
  - **References:** `REF-AUTH`, `PRM-PASSWORDLESS`, `PRM-RECOVERY`

### Session management

- **SEC-SESSION-1** The server MUST invalidate a session immediately on sign-out (FR-1.5); subsequent requests presenting that session MUST be rejected. Client-side state clearing alone is insufficient.
  - **Applies to:** All authenticated API operations
  - **Verification:** Test replaying a signed-out session credential against protected endpoints
  - **References:** `REF-SESSION`
- **SEC-SESSION-2** The server MUST enforce an absolute session lifetime and MUST enforce an idle timeout (raised from SHOULD per T-8), both server-side, at the FR-1.10 values.
  - **Applies to:** Identity & session handling
  - **Verification:** Clock-advanced tests asserting expiry regardless of client behavior
  - **References:** `REF-SESSION`, `REF-63B-4`
- **SEC-SESSION-3** Sessions use the backend-for-frontend pattern (resolves SQ-3): every Cognito ceremony and token exchange terminates server-side at the API, which issues its own opaque session identifier; Cognito tokens MUST never reach a browser or mobile client. The API MUST issue different server-side session classes for passkey authentication and email-OTP bootstrap/recovery, and its centralized enforcement layer MUST allow the latter to call only the passkey-registration operation SEC-AUTHN-6 permits. For the web client the session identifier MUST be carried in an HttpOnly, Secure, SameSite=Lax cookie with CSRF defenses applied (`PRM-CSRF`). The mobile client MUST present the same opaque identifier as an `Authorization` bearer header on every request and MUST NOT place it in a cookie or any other ambient credential store, holding it at rest per SEC-SESSION-6 (resolves SQ-18). CSRF defenses are therefore web-only by construction rather than by omission: only the cookie transport is attached ambiently by the user agent, so no cross-site request can carry the mobile credential. Session identifiers MUST be opaque, generated with a cryptographically secure random source, transmitted only over TLS, never placed in URLs, and never written to logs (NFR-1.7). This rule governs trust boundary 4 (system ↔ identity provider).
  - **Applies to:** Client ↔ API boundary
  - **Verification:** Cookie-attribute and CSRF tests; token-entropy and log-scan checks; test that no Cognito token is exposed to either client; test that the mobile transport is a bearer header and sets no ambient credential; tests that an email-OTP session can register one passkey and cannot call any other endpoint
  - **References:** `REF-SESSION`, `REF-REST`, `PRM-CSRF`
- **SEC-SESSION-4** The session identifier MUST be regenerated on successful authentication so a pre-authentication session value never survives into an authenticated session.
  - **Applies to:** Identity & session handling
  - **Verification:** Test comparing session identifiers before and after authentication
  - **References:** `REF-SESSION`
- **SEC-SESSION-5** Completion of account recovery (FR-1.6), an email-address change (FR-1.7), or any credential registration or revocation (FR-1.8) MUST invalidate all other active sessions. (Email change added per T-3: without it, an attacker who changes the address from a stolen session keeps every other session alive.)
  - **Applies to:** Identity & session handling
  - **Verification:** Test that concurrent sessions are invalidated after account recovery, email change, or credential change
  - **References:** `REF-SESSION`
- **SEC-SESSION-6** Mobile clients MUST keep session credentials only in platform secure storage (iOS Keychain, Android Keystore-backed storage); they MUST NOT be written to shared preferences, plain files, or shared multiplatform code storage. The same storage holds the SEC-AUTHN-11 device identifier. The credential is read from it and attached explicitly to each request as SEC-SESSION-3's `Authorization` bearer header — never by an ambient mechanism the platform would replay on its own.
  - **Applies to:** Mobile client (Compose MP)
  - **Verification:** Code review of the storage abstraction; device-storage inspection tests asserting the session credential and device identifier rest only in platform secure storage
  - **References:** `PRM-KMP`, `REF-SESSION`
- **SEC-SESSION-7** The mobile client MUST enforce the platform security posture (resolves SQ-14): re-lock after 5 minutes in the background, requiring biometric or passkey resume; obscure the app's task-switcher snapshot; exclude app data from OS backups; keep sensitive content out of OS notifications; and flag sensitive fields to platform keyboards so typed health terms are not retained in keyboard caches (T-8, T-51). A field is sensitive when its entity carries the sensitivity classification `REQUIREMENTS.md` **Data Entities** records — the same classification `DESIGN.md` **On-Screen Privacy** masks against, so the keyboard flag and the masking convention cannot drift apart. Client authenticity and update integrity are provided by store distribution and code signing through the App Store and Google Play (`ARCHITECTURE.md`; T-36): the distribution signing keys MUST be held by the platforms — Google Play App Signing and Apple-managed certificates — and CI MUST hold upload keys only, injected from AWS Secrets Manager over the GitHub Actions OIDC path (SEC-SECRET-1, SEC-DEPLOY-3), so a compromised pipeline cannot produce a signed release impersonating the app (T-35). If the online-only decision is ever revisited, any personal data cached on-device MUST use platform secure storage with encryption at rest (T-37). `DESIGN.md` owns the user-facing masking and re-lock conventions (DQ-6).
  - **Applies to:** Mobile client (Compose MP); CI/CD (GitHub Actions)
  - **Verification:** Device tests of re-lock timing, snapshot obscuring, backup exclusion, notification content, and sensitive-field keyboard flags across the classified entities; signing-custody review asserting CI holds no distribution key
  - **References:** `PRM-KMP`, `REF-SESSION`

### Authorization

- **SEC-AUTHZ-1** The API MUST verify on every operation that the authenticated user owns the target record — established server-side from persisted ownership data, never from client-supplied values — before performing it (FR-1.9).
  - **Applies to:** Every CRUD/export operation on every entity
  - **Verification:** Automated per-endpoint tests using owned and non-owned record identifiers
  - **References:** `REF-ASVS-5`, `REF-API-2023`, `PRM-ABAC`
- **SEC-AUTHZ-2** Authorization MUST be deny-by-default and fail closed: a request is refused unless an explicit ownership match succeeds, and any error or unresolvable state in an authorization path MUST result in denial, never a fall-through permit.
  - **Applies to:** REST API application authorization paths
  - **Verification:** Fault-injection tests in authorization code paths asserting denial
  - **References:** `PRM-ABAC`, `PRM-QUALITY`, `PRM-SSWEB`
- **SEC-AUTHZ-3** A request targeting another user's record MUST fail with a response indistinguishable from the record not existing (FR-1.9).
  - **Applies to:** All API responses on authorization failure
  - **Verification:** Response-equivalence tests: non-owned vs. non-existent identifiers
  - **References:** `REF-API-2023`, `REF-ERROR`
- **SEC-AUTHZ-4** Object-level authorization MUST NOT depend on identifiers being unguessable; every file fetch and record access is authorized regardless of how the identifier was obtained.
  - **Applies to:** Documents, export artifacts, and all record endpoints
  - **Verification:** Tests fetching known-valid foreign identifiers; static check that no unauthenticated file routes exist
  - **References:** `REF-API-2023`, `REF-ASVS-5`
- **SEC-AUTHZ-5** Ownership checks MUST be centralized in a single enforcement layer that every endpoint passes through, so no individual handler can omit the check.
  - **Applies to:** REST API application
  - **Verification:** Architecture review; static analysis that no endpoint bypasses the enforcement layer
  - **References:** `PRM-ABAC`, `PRM-QUALITY`

### HTTP/API boundary

- **SEC-HTTP-1** (**NFR-1.1**) All client–server communication MUST use TLS 1.2 or higher; the system MUST NOT serve any functionality over cleartext connections. Protocol and cipher configuration beyond that floor follows the AWS-managed TLS security policies at the CloudFront edge and load balancer, both pinned to `TLSv1.2_2021` — the current strong managed policy, whose floor is TLS 1.2 with a modern cipher set (resolves the SQ-5 portion). The same edge runs AWS WAF with the AWS Managed Rules **Common Rule Set** and **Known Bad Inputs Rule Set** plus a rate-based rule for volumetric protection (T-21); these are an outer layer only and MUST NOT be relied on in place of the server-side enforcement SEC-TRUST-1 requires or the application limits SEC-HTTP-6 sets.
  - **Applies to:** Client ↔ API boundary
  - **Verification:** TLS configuration scan asserting the pinned policy at both terminators; test that no cleartext endpoint serves functionality; WAF rule-group and rate-based-rule configuration review
  - **References:** `REF-REST`, `REF-ASVS-5`
- **SEC-HTTP-2** The API MUST validate the HTTP method and declared content type of each request, rejecting unsupported methods and mismatched or unexpected content types rather than content-sniffing.
  - **Applies to:** All REST endpoints
  - **Verification:** Tests sending wrong-method and wrong-content-type requests
  - **References:** `REF-REST`
- **SEC-HTTP-3** Browser-delivered responses MUST carry security headers for the React web client (resolves SQ-4; CQ-2 resolved in `ARCHITECTURE.md`), at these values: a Content-Security-Policy of `default-src 'none'` with explicit self-only allowances for script, style, image, and connect sources and `frame-ancestors 'none'`, carrying no `unsafe-inline`, no `unsafe-eval`, and no wildcard source; `X-Content-Type-Options: nosniff`; `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`; `Referrer-Policy: strict-origin-when-cross-origin`; and a `Permissions-Policy` denying camera, microphone, geolocation, and payment. API responses rendered in browsers MUST carry the same protections.
  - **Applies to:** Web client delivery and API responses rendered in browsers
  - **Verification:** Header assertions in integration tests covering each listed header and its exact value, including that the policy contains no `unsafe-*` keyword and no wildcard source
  - **References:** `REF-XSS`, `PRM-XSS`, `REF-REST`
- **SEC-HTTP-4** Cross-origin resource sharing MUST NOT be enabled: the API serves same-origin consumers only, recorded as final. Any future cross-origin consumer MUST explicitly reopen this decision through a security review, with allowed origins as an explicit allowlist.
  - **Applies to:** REST API responses
  - **Verification:** Header scan asserting no permissive CORS in default configuration
  - **References:** `REF-REST`
- **SEC-HTTP-5** Every API response MUST carry `Cache-Control: no-store` and MUST NOT be cacheable by browsers or intermediaries.
  - **Applies to:** All API responses
  - **Verification:** Cache-header assertions across the complete API surface
  - **References:** `PRM-API`, `REF-REST`
- **SEC-HTTP-6** The API SHOULD enforce request-rate and resource limits beyond the FR-1.4 authentication throttle, and MUST enforce the outbound-email cap (raised per T-30) (resolves SQ-9). Initial values, recorded as tunable operational limits — changing a value is an operational change, not a specification change: API requests 600/min per user; authentication ceremonies 10/min per source IP with backoff (a valid passkey ceremony is never blocked, SEC-AUTHN-4); registrations 5/hour per source IP; full-account exports 2/day; case PDF and CSV exports 20/day; outbound email 20/day per recipient address as a hard cap; uploads 2 GB/day per user. Every "per day" limit is a **rolling 24-hour window** — the count is of events in the preceding 24 hours, never since a calendar-day boundary — so an attacker cannot draw two allowances by straddling midnight and a legitimate user is never blocked waiting for a reset that has not happened in their timezone. The SEC-AUTHN-11 security notices are exempt from the 20/day per-recipient email cap: they are the channel that warns a victim of a takeover in progress, and SEC-AUTHN-11 already forbids suppressing them. Reminder mail and every other message stay capped.
  - **Applies to:** All API operations; background jobs that send email
  - **Verification:** Load tests asserting enforcement at the recorded limits, that a daily limit releases by rolling 24-hour window rather than at a calendar boundary, and that a SEC-AUTHN-11 notice is still delivered once the per-recipient cap is reached
  - **References:** `REF-API-2023`, `PRM-RATE`

### Input validation

- **SEC-INPUT-1** The API MUST validate all untrusted input server-side at boundary 1, for both format and business meaning: accident/onset dates not in the future, resolved in the timezone FR-2.1 and FR-4.1 name; severity integer 0–10 (FR-4.1, FR-4.3); expense and reimbursement amounts at the precision and bounds FR-7.1 and FR-7.4 state; enumerated categories/statuses/roles (FR-3.2, FR-5.2, FR-6.1, FR-7.1); the FR-1.12 profile settings — timezone as an IANA identifier, locale from the NFR-5.4 supported set; file type/size/quota (FR-3.1, FR-3.10); and the per-field length limits `REQUIREMENTS.md` **Data Entities** records. Free-text fields (journal, notes) accept broad legitimate character sets within those limits; validation MUST NOT substitute for output encoding.
  - **Applies to:** Every write operation at the Client ↔ API boundary
  - **Verification:** Per-field negative tests via direct HTTP
  - **References:** `REF-INPUT`, `REF-PC-2024`, `PRM-QUALITY`
- **SEC-INPUT-2** All database access MUST use parameterized statements or an equivalent mechanism separating code from data; dynamic query construction from user input MUST NOT occur, and dynamic sort/filter identifiers MUST map through a server-side allowlist.
  - **Applies to:** API application and background worker access to the RDBMS
  - **Verification:** Static analysis for string-built queries; injection test suite asserting payloads are treated as literals
  - **References:** `PRM-SQLI`, `REF-INPUT`, `PRM-QUARKUS`
- **SEC-INPUT-3** Upload acceptance MUST be decided by server-side inspection of file content against the allowed type list (FR-3.1), not by file extension or client-declared content type alone, with size limits enforced before full buffering. Inspection uses the upload-type inspection technology `ARCHITECTURE.md` selects (Apache Tika) — magic bytes and container inspection; a mismatch with the declared or allowed types MUST be rejected (T-24).
  - **Applies to:** Document upload endpoint
  - **Verification:** Tests uploading mismatched extension/content pairs and oversize streams
  - **References:** `PRM-UPLOAD`, `REF-INPUT`
- **SEC-INPUT-4** Request bodies MUST bind to explicit request models; every unknown field and every server-controlled field (owner, identifiers, timestamps) MUST cause the request to be rejected and MUST never be bound to a persisted entity.
  - **Applies to:** All REST write endpoints
  - **Verification:** Tests submitting unknown or server-controlled fields and asserting request rejection with no state change
  - **References:** `REF-API-2023`, `PRM-API`, `PRM-QUARKUS`

### File and document handling

- **SEC-FILE-1** (**NFR-1.4**) Uploaded files and export artifacts MUST NOT be retrievable via unauthenticated or non-authorized requests: they MUST be stored only in the private file store and retrieved only by streaming through authenticated, owner-authorized API endpoints, with no public or guessable URLs. Every file fetch is subject to FR-1.9.
  - **Applies to:** File store; document/export download paths
  - **Verification:** Infrastructure review; tests fetching storage paths directly without API authorization
  - **References:** `REF-ASVS-5`, `PRM-UPLOAD`, `REF-API-2023`
- **SEC-FILE-2** Files served to clients MUST satisfy SEC-TRUST-3: delivery streams through authenticated API endpoints (SEC-FILE-1) with `Content-Disposition: attachment` as the default; inline/in-app viewing (FR-3.5) is permitted only for safe, non-active types rendered in a sandboxed viewer context; and uploaded content is never served as active content from the application origin (resolves the CQ-2/SQ-4 dependency).
  - **Applies to:** In-app viewing (FR-3.5) and downloads
  - **Verification:** Tests that uploaded HTML/SVG/JS renders inert in the app origin
  - **References:** `PRM-UPLOAD`, `REF-XSS`, `PRM-QUARKUS`
- **SEC-FILE-3** Stored files MUST use server-generated storage names; the original filename is kept only as sanitized display metadata (FR-3.2 title default) and MUST never be used as a storage path.
  - **Applies to:** File store; upload pipeline
  - **Verification:** Storage-layout review; path-traversal tests with hostile filenames
  - **References:** `PRM-UPLOAD`
- **SEC-FILE-4** A file flagged by malware scanning (FR-3.9) MUST NOT become retrievable or exportable; flagged files are quarantined. Scanning ships in v1 using the engine `ARCHITECTURE.md` selects (ClamAV), running in the isolated background worker (SEC-FILE-6) (resolves SQ-10).
  - **Applies to:** Upload pipeline; background processing
  - **Verification:** Test with a standard detection-test file
  - **References:** `PRM-UPLOAD`
- **SEC-FILE-5** Downloads MUST return the byte-identical original (FR-3.5); the system MUST NOT transform stored originals in place, preserving the integrity of evidence documents. The system MUST compute a SHA-256 content hash at upload, store it, and surface it to the user so byte-identity is independently verifiable (resolves the SQ-13 hashing element; T-14, T-47).
  - **Applies to:** File store; download path
  - **Verification:** Round-trip hash comparison tests; test that the stored SHA-256 matches the uploaded bytes and is displayed
  - **References:** `REF-ASVS-5`
- **SEC-FILE-6** Server-side processing that parses attacker-influenced file bytes — malware scanning (FR-3.9), any future FR-3.4 file-content indexing (none in v1), and the embedding of user files and text during FR-9.1/FR-9.2 generation — MUST run isolated from the API application with the least store access the job requires, so a parser or decoder exploit cannot gain the background worker's read-all/delete-all reach across boundary 2 (T-16, T-17). Isolation is provided by the separate background worker service (`ARCHITECTURE.md`), which runs apart from the API application (resolves the SQ-5/execution-model dependency). The in-app viewing path (FR-3.5) is covered by the SEC-FILE-2 delivery mechanism — sandboxed viewing of safe types — which addresses client decoder/codec exploitation, not only script execution. Because SEC-FILE-5 forbids sanitizing transforms, a format-valid weaponized upload is stored and re-served intact and may be bundled into exports; malware scanning (FR-3.9, SEC-FILE-4) ships in v1 to reduce this redistribution path.
  - **Applies to:** Background processing; File store; Document upload/download flow
  - **Verification:** Architecture review of parsing isolation and store-scope; SEC-FILE-2 mechanism review for decoder risk
  - **References:** `PRM-UPLOAD`, `REF-INPUT`, `PRM-QUARKUS`

Titles, notes, tags, journal entries, contact fields, and filenames MUST be rendered as text with context-appropriate encoding in every client surface; no interface may interpret or inject user data as Markdown, rich text, or raw HTML/DOM markup. Introducing another content format requires a security review and a requirements decision.

- **SEC-OUT-2** Generated exports MUST treat user data as inert data: CSV output (FR-7.6, FR-9.2) MUST neutralize spreadsheet-formula injection, and PDF generation (FR-9.1) MUST NOT interpret user text as markup or code.
  - **Applies to:** REST API CSV export; background PDF/export pipeline
  - **Verification:** Exports containing formula-prefix and markup payloads open inert
  - **References:** `REF-XSS`, `REF-INPUT`
- **SEC-OUT-3** A user-supplied value MAY be rendered as a link only when its scheme is `https`, `mailto`, or `tel`; every other scheme, including `http` and script-capable schemes, MUST remain inert text.
  - **Applies to:** Clients rendering contact and note fields

### Data protection and privacy

- **SEC-DATA-1** (**NFR-1.2**) All stored personal data — database contents, uploaded files, export artifacts, backups, and any additional store that holds personal data (e.g., a future search index) — MUST be encrypted at rest; encryption is managed through AWS KMS (managed PostgreSQL and S3 server-side encryption with KMS keys), with key custody separated from the data plane — KMS key administration is held apart from the data-plane service identities — so at-rest encryption also constrains a privileged infrastructure operator (resolves the SQ-5 portion; T-13, T-19, T-20).
  - **Applies to:** Data persistence; file store; backups
  - **Verification:** Infrastructure review of KMS key policies and custody separation
  - **References:** `REF-ASVS-5`, `PRM-TF`
- **SEC-DATA-2** (**NFR-2.3**) The system MUST collect and store only data that serves the functional requirements, and MUST treat all of it as sensitive personal data (D-5) regardless of which regulatory regime is ultimately targeted.
  - **Applies to:** All entities and any telemetry
  - **Verification:** Schema and field review against REQUIREMENTS.md **Data Entities**
  - **References:** `REF-ASVS-5`, `REF-63B-4`
- **SEC-DATA-3** (**NFR-2.1**) Personal data MUST be used solely to provide the service to its owner; it MUST NOT be sold or shared with third parties, and authenticated screens MUST NOT include third-party advertising or marketing trackers.
  - **Applies to:** All clients and server integrations
  - **Verification:** Network-traffic inspection of authenticated sessions; dependency review
  - **References:** `REF-ASVS-5`
- **SEC-DATA-4** (**NFR-2.4**) Data portability and erasure MUST be honored through full-account export (FR-9.2) and account deletion (FR-9.3), within the timelines those requirements state.
  - **Applies to:** Background processing; all stores
  - **Verification:** Deletion tests asserting absence after purge windows, including the file store
  - **References:** `REF-ASVS-5`
- **SEC-DATA-5** (**NFR-2.5**) In the event of a personal-data breach, affected users MUST be notified without undue delay. Incident response is operator-owned with a written runbook (resolves SQ-11): alerting (CloudWatch/GuardDuty) → triage within 24 hours → scoping → notification of affected users by email within 72 hours of confirming a breach (the D-10 global bar) → post-incident review; the operator is the named incident-response role. Breach handling covers the account owner as the sole data subject (SQ-15, Security Profile).
  - **Applies to:** Incident response (operator-owned runbook)
  - **Verification:** Incident-response runbook review and tabletop exercise
  - **References:** `REF-ASVS-5`
- **SEC-DATA-6** Outbound email MUST carry the minimum personal data needed for its purpose; health data and document contents MUST NOT appear in email bodies or subjects. Authentication mail MUST contain only its purpose, the one-time code, its expiry, and origin-safety guidance. Reminder and notification emails MUST carry only the existence of an item, its date/time, and a link to in-app detail — never titles, provider names, or purposes (resolves SQ-12). In-app feed items are modeled as a Data Entity in `REQUIREMENTS.md` (T-43).
  - **Applies to:** System ↔ email provider boundary
  - **Verification:** Template review; tests asserting excluded fields never reach the email boundary
  - **References:** `REF-LOG`, `REF-ASVS-5`
- **SEC-DATA-7** (**NFR-2.2**) A privacy policy MUST be viewable before registration, and registration MUST record the user's acceptance of it. The policy MUST disclose the security event log's retention and its pseudonymized survival of account deletion (SEC-LOG-1; discloses the SQ-7 outcome) and the device-recognition records SEC-AUTHN-11 keeps — the `Device` entity in `REQUIREMENTS.md` **Data Entities** — stating that the system remembers which devices have signed in so it can warn the owner about one it does not recognize; and a material change to the policy MUST re-notify users and record fresh acceptance where the change is material (T-41).
  - **Applies to:** Registration flow; Web client; Mobile client
  - **Verification:** Functional test that registration is refused without recorded acceptance; test that a material policy change triggers re-notification and re-acceptance
  - **References:** `REF-ASVS-5`
- **SEC-DATA-8** A production restore under NFR-3.2 MUST NOT silently reintroduce security or privacy state the user changed since the backup point (T-32, T-48). On restore the system MUST invalidate all sessions and MUST drive the corresponding re-revocation at the managed identity provider, because passkey credential material is held there and not in the restored database (SEC-AUTHN-2, `ARCHITECTURE.md`) — without it a restore silently re-arms a credential the user revoked precisely because it was compromised (T-48) — and MUST re-apply, where the affected records survive, the credential revocations (FR-1.8) and account/record deletions (FR-2.6, FR-3.8, FR-9.3) recorded after the backup point; it SHOULD notify the affected user that a restore occurred so they can re-check their credential list. Backups MUST bound how long record-level deletions persist — purged records MUST be unrecoverable from backups no later than 30 days after the purge (resolves the CQ-3 backup bound; T-33), with mechanics on the AWS-managed backup facilities — and restore-test copies materialized under NFR-3.2 MUST meet production data controls and be destroyed after verification (T-31, T-33). Responsibility for post-restore reconciliation is assigned to Background processing (`ARCHITECTURE.md`).
  - **Applies to:** Data persistence; File store; Background processing; backups
  - **Verification:** Restore drills asserting post-backup revocations and deletions do not resurrect and that all sessions are invalidated; backup-retention and restore-test-destruction review
  - **References:** `REF-ASVS-5`, `REF-63B-4`

### Logging and error handling

- **SEC-LOG-1** (**NFR-1.6**) The system MUST keep a security event log covering at minimum sign-ins, failed sign-ins, lockouts, credential registration and revocation (FR-1.8), email changes, account recovery, exports, account deletions, and — added per T-11/T-12 — case, document, and record deletion (FR-2.6, FR-3.8), trash restoration, and permanent purge execution (FR-2.6, FR-3.8, FR-9.3), and — added per T-49 — a change to a notification preference such as the FR-5.6 account-wide email-reminder toggle, since switching reminders off is a plausible first move for an attacker holding a stolen session who wants insurance and legal deadlines to lapse unnoticed; each with timestamp and source IP, retained at least 12 months. "Exports" covers every export form — full-account archive (FR-9.2), case-summary PDF (FR-9.1), and expense CSV (FR-7.6) — so no export escapes the reviewable record. Authorization denials SHOULD also be logged. On account deletion (FR-9.3), log entries survive for the remainder of their 12-month retention in pseudonymized form: the user identifier MUST be replaced with an unlinkable token, the email address removed, and source IPs truncated; SEC-DATA-7's policy discloses this (resolves SQ-7; T-26). Each entry MUST be written by the component that performed the action — Identity & session handling for ceremonies and session events, the REST API application for interactive operations, and Background processing for its own purges, deletions, and export generation — through the single shared append-only client SEC-LOG-4 defines, so no component depends on another to record what it did. SEC-LOG-4 governs what happens when that write fails.
  - **Applies to:** Identity & session handling; REST API application; Background processing
  - **Verification:** Tests asserting a log entry per listed event type, including that background-initiated purges, deletions, and exports are logged by the worker itself
  - **References:** `REF-LOG`, `PRM-ABAC`
- **SEC-LOG-2** (**NFR-1.7**) Application and security logs MUST NOT contain credentials, session tokens, file contents, or health data; logs record identifiers and event metadata only.
  - **Applies to:** All server components
  - **Verification:** Log-content scans in integration tests exercising health and document flows
  - **References:** `REF-LOG`
- **SEC-LOG-3** The user MUST be able to view their own security activity in-app (raised from SHOULD per T-27), giving them a first-party channel to detect account misuse that an attacker operating a stolen session cannot suppress. The view MUST surface at minimum the SEC-LOG-1 events attributable to the account (sign-ins, credential and email changes, exports, deletions). It MUST read a first-party projection of those entries held in the relational store and written alongside each append-only entry (`ARCHITECTURE.md` owns the read path), so the user-facing query path never holds read access to the tamper-evident store SEC-LOG-4 protects; the projection is derived state and the append-only log stays the record of authority. The view MUST cover the full 12-month SEC-LOG-1 retention window rather than a shorter recent slice, so a takeover months earlier is still discoverable, and MUST display source IPs truncated exactly as SEC-LOG-1 truncates them on deletion — enough for an owner to recognize an unfamiliar network, not a precise movement history handed to whoever is holding the session.
  - **Applies to:** REST API application; Data persistence (projection); clients
  - **Verification:** Functional test of the security-activity view showing the listed event types across the full 12-month window with truncated source IPs; review asserting the view's query path has no read access to the append-only store
  - **References:** `REF-LOG`
- **SEC-LOG-4** The security event log MUST be tamper-evident and append-only, with write access separated from the components that generate its entries, so a compromise of the REST API application or a privileged infrastructure operator cannot silently rewrite or delete the audit trail that would prove an exfiltration or takeover (T-34) — integrity that also matters as the victim's own evidence in an adversarial dispute. The mechanism is CloudWatch Logs with IAM write-separation: the log-writing path holds append-only permissions, and no component that generates entries can modify or delete them (resolves the SQ-5 portion). Every generating component writes through one shared append-only client (SEC-LOG-1), which holds that append-only credential and nothing wider. A write that cannot be completed fails closed: a security-significant operation — authentication, credential change, export, deletion, purge — MUST be refused rather than performed unlogged, on the SEC-AUTHZ-2 doctrine that an unresolvable state in a security path denies. So that a momentary sink outage does not stop the product, the client MAY hold entries in a short bounded local buffer and retry; the refusal takes effect once that buffer is full or its bound elapses.
  - **Applies to:** Identity & session handling; REST API application; Background processing; Data persistence
  - **Verification:** Tests that log entries cannot be modified or deleted through the API; design review of write-path separation; fault-injection tests asserting that a security-significant operation is refused when its entry cannot be written, and that a transient sink outage is absorbed by the bounded buffer without losing entries
  - **References:** `REF-LOG`, `PRM-ABAC`
- **SEC-ERR-1** Client-facing errors MUST NOT expose stack traces, framework identifiers, queries, internal paths, or any other internal state; they carry only the plain-language content NFR-5.3 requires. Full diagnostics are retained server-side subject to SEC-LOG-2, produced through a single centralized exception-handling path.
  - **Applies to:** All API responses and client error surfaces
  - **Verification:** Error-path tests (including malformed uploads and storage failures) asserting sanitized responses
  - **References:** `REF-ERROR`, `PRM-QUALITY`

  - **Verification:** DNS/sender-authentication configuration review at provider selection; template review that no mail solicits secrets; tests that a single hard bounce and that three consecutive soft failures each raise the in-app notice, and that one or two soft failures do not
  - **References:** `REF-AUTH`, `REF-SUPPLY`, `REF-SECRETS`

Threats `T-1`–`T-51` were produced by six methodology lenses (STRIDE over identity/session, over the API/data/file core, and over background/email/deployment; LINDDUN privacy analysis; attack-tree analysis of the four highest-value adversary objectives; and document/architecture absorption), consolidated, and adversarially verified against these documents. Each row names a specific documented element, describes the threat as actor + capability + impact, cites only existing controls that genuinely cover it, and states the gap with a proposed change at the level the documents support. ## Dependency Security Rules

Prospective rules; no dependency exists yet and none has been assessed. Supply-chain references: `REF-SUPPLY`, `REF-VULNDEP`, `REF-CICD`, `REF-SSDF`.

- **DEP-1** The project MUST NOT add a dependency when the standard library or a small amount of straightforward, non-security-sensitive first-party code is safer and sufficient. The project MUST NOT replace vetted cryptography, authentication, authorization, protocol parsing, output encoding, HTML sanitization, or other security-critical functionality with custom code merely to avoid a dependency.
- **DEP-2** The project SHOULD prefer zero new dependencies. Every new dependency MUST be justified in the pull request description, including its purpose and why existing code or platform functionality is insufficient.
- **DEP-3** A new dependency MUST show evidence of active maintenance through a stable release, security response, or substantive maintainer activity within the previous 12 months. A mature project with less frequent releases requires an explicit documented exception and evidence that security reports are still handled.
- **DEP-4** The project MUST use the latest stable release from the latest actively supported major version unless a documented compatibility constraint requires another actively supported major version. Deprecated, abandoned, end-of-life, or pre-release packages MUST NOT be introduced into production.
- **DEP-5** Before a dependency is added or updated, direct and transitive dependencies MUST be checked for known vulnerabilities. A dependency with a known unpatched vulnerability applicable to the intended use MUST NOT be introduced without explicit, time-bounded risk acceptance, documented compensating controls, and a remediation plan. Ongoing patching of known-vulnerable dependencies is governed by SEC-DEPLOY-4.
- **DEP-6** Dependency review MUST include the complete transitive dependency graph. A small direct dependency with a disproportionately large, opaque, abandoned, or unvetted transitive tree SHOULD be rejected.
- **DEP-7** Production builds MUST resolve dependencies to exact versions through a committed lockfile or equivalent ecosystem mechanism. Production and CI builds MUST use frozen or reproducible dependency resolution and MUST NOT resolve floating versions at build or deployment time.
- **DEP-8** When multiple suitable libraries exist, the project SHOULD prefer the library with the narrowest required scope, smallest dependency tree, active security response process, clear provenance, and established security track record.
